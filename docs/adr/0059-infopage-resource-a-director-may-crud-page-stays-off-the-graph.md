# InfoPage is exposed at `/api/infoPages`; a Director may fully CRUD it; `Page` stays off the resource graph

P5-16 (#21) exposes `InfoPage` (CONTEXT.md) as a JSON:API resource, scoped Admin/Director the same way
`/api/events` already is. Scope is the entity itself (Title, MarkdownContent, EventId) only - Placement
(which Tab, optionally which Sub Tab) is a separate resource, tracked as P5-18/P5-19/P5-20 (#86/#91/#92).

## A Director may fully CRUD an InfoPage on an assigned Event

ADR-0031 narrowed a Director's write access to Event details (Name/Slug/Passcode/Status/dates) to Admin-only,
and explicitly deferred the same question for every other Event-scoped resource: "future Event-scoped
resources (e.g. Pages, Activities) each make their own call." This is that call for InfoPage, and it goes the
other way: a Director assigned to an Event may create, read, update, and delete that Event's InfoPages, with
no narrower carve-out for delete.

The two resources aren't actually the same kind of write. Event details are platform-level facts about the
gathering itself; ADR-0031 narrowed them to Admin-only partly because doing otherwise "makes an Admin a
bottleneck for every other Event-scoped write a Director will eventually need (Pages, Activities)" - authoring
InfoPage content *is* that eventual write, and CONTEXT.md's Director entry casts a Director as the person who
runs their assigned Event's Leaders Guide day to day. Gating InfoPage authorship through an Admin would
recreate the exact bottleneck ADR-0031 was trying to avoid, just one resource later than it named.

Delete carries no separate carve-out because the asymmetry doesn't hold up: ADR-0045 makes every destructive
action a hard delete with no undo, but a Director can already destroy an InfoPage's content just as
permanently by PATCHing `markdownContent` to empty - nobody proposes gating that. The actual protection
against an accidental loss is the dashboard's shared confirm dialog (ADR-0045), not an API-level role split.

Codified as `InfoPageAccessPolicy.CanWrite`, which is deliberately `EventAccessPolicy.CanRead`, not
`EventAccessPolicy.CanUpdate` - read and write coincide for InfoPage, unlike Event.

## `Page` becomes `Identifiable<Guid>` but is removed from the resource graph

Making `InfoPage` a resource means giving it (or its base `Page`) an `Id` JsonApiDotNetCore recognizes, which
means `Page` inheriting `Identifiable<Guid>`. ADR-0055 flagged this as an open question for P5-16 to resolve,
on the assumption that inheriting `Identifiable<Guid>` alone would auto-expose `/api/pages` the moment `Page`
joined the EF model - stated as fact in ADR-0055's body and in `Page`'s own remarks at the time.

**That assumption is wrong, and we verified it directly against the JsonApiDotNetCore 5.11.0 assemblies before
building on it.** `AddJsonApi<TDbContext>` does walk every entity type in the EF model and register any
`IIdentifiable` type it finds in the resource graph - but graph membership alone creates no route. A
JsonApiDotNetCore controller is generated by its source generator specifically off `[Resource]`
(`JsonApiDotNetCore.SourceGenerators`'s own diagnostic: *"Type '{0}' must implement IIdentifiable&lt;TId&gt;
when using ResourceAttribute to auto-generate ASP.NET controllers"*) - a graph-registered type with no
`[Resource]` gets no controller and 404s on every route, exactly like `/api/pages` already did before this
ticket. ADR-0055's "`[Resource]` only customizes naming, it doesn't gate exposure" sentence had the mechanism
backwards; corrected here.

We still don't want `Page` sitting in the graph as a live `ResourceType`, even though no controller would ever
expose it - it would become `InfoPage.BaseType`, dragging in JsonApiDotNetCore's resource-inheritance
machinery (derived-field validation, polymorphic `isType()` filter semantics, `fields[pages]` handling) that
nothing in this codebase exercises or has tested, purely as a side effect of `Page` needing an `Id` at all. So
`Page` is explicitly removed from the resource graph in `Program.cs`:

```csharp
builder.Services.AddJsonApi<VirtualLeadersGuideDbContext>(
    options => { options.Namespace = "api"; options.IncludeTotalResourceCount = true; },
    resources: resourceGraph => resourceGraph.Remove<Page>());
```

`[NoResource]` was considered and rejected as unusable for this: its `[AttributeUsage]` is `Inherited = true`,
so putting it on `Page` would suppress `InfoPage` too.

`InfoPage` is consequently a plain root resource, not the derived half of a resource-inheritance hierarchy -
confirmed by a runtime check that `IResourceGraph.FindResourceType(typeof(Page))` is `null` while
`FindResourceType(typeof(InfoPage))` is not (`PageEntitiesAreNotJsonApiResourcesShould`).

## Single-resource scoping costs one synchronous database lookup

`EventResourceDefinition.OnApplyFilter` decides a single-resource 403 by checking `IJsonApiRequest.PrimaryId`
directly against the caller's assigned Event ids, because for `/api/events` the primary id *is* the Event id.
For `/api/infoPages` the primary id is the InfoPage's own id, and the policy check needs the *Event* id the
row belongs to - which means a database read has to happen before the authorization decision can be made.

`OnApplyFilter` is synchronous, and JsonApiDotNetCore 5.11's `IResourceDefinition<TResource,TId>` has no async
read hook at all (`OnPrepareWriteAsync` and `OnWritingAsync` exist for writes; there is nothing equivalent for
a plain read). We resolved this with a synchronous EF Core scalar query - genuine sync I/O, not
sync-over-async - run only for a non-Admin single-resource request:

```csharp
_dbContext.InfoPages.AsNoTracking().Where(page => page.Id == infoPageId).Select(page => page.EventId).FirstOrDefault();
```

Two alternatives were considered and rejected outright, not merely deprioritized:

- **Throwing the 403 from `OnSerialize` instead**, where an async read would be trivial - infeasible, not just
  risky. JsonApiDotNetCore's exception filter (`AsyncJsonApiExceptionFilter`) is an ASP.NET Core MVC
  `IAsyncExceptionFilter`, and MVC exception filters do not run during result execution or output formatting;
  `OnSerialize` is invoked from the output formatter itself. An exception thrown there surfaces as a 500, not
  a 403.
- **A custom `JsonApiResourceService<InfoPage, Guid>` overriding `GetAsync`**, where the check could be
  genuinely async - feasible, but rejected: it would split authorization across two types, directly against
  ADR-0031's "authorization lives in a resource definition," and it wouldn't even replace this resource
  definition, since the collection filter and every write check still have to live here regardless.

A missing row resolves the lookup to `Guid.Empty`, which fails every non-Admin's access check the same way an
out-of-scope row would - a non-Admin gets 403 for a nonexistent id, not a distinguishing 404. This matches
`EventResourceDefinition`'s existing posture for a Director probing an unknown Event id, and ADR-0031's
argument for 403-over-404 on this exact shape. An Admin still gets a real 404, since the Admin short-circuit
runs before this lookup.

## Considered options

- **Scoping the single-resource query and letting it 404 instead of 403** - rejected: contradicts P5-16's
  acceptance criteria, which specify 403 for an out-of-scope request.
- **Reusing `EventAccessPolicy` directly instead of a new `InfoPageAccessPolicy`** - rejected: that type's
  `CanCreate`/`CanUpdate`/`CanDelete` encode Event-details semantics that are wrong for InfoPage (see above);
  a separate policy type is the same precedent `RoleGrantAccessPolicy`/`ApplicationUserAccessPolicy` already
  set. It delegates to `EventAccessPolicy` rather than re-parsing claims, so the two can't drift apart.

## Consequences

- A non-Admin cannot distinguish "this InfoPage is out of my scope" from "this InfoPage doesn't exist" - both
  are 403. Accepted for the same reason ADR-0031 accepted it for Event: the alternative leaks which ids are
  real to a caller who can't read them anyway.
- ADR-0033's "a caller whose visible set is always empty gets 403 on every shape" rule does not apply here - a
  Director's InfoPage visibility is sometimes non-empty, the same "ordinary narrowing" case ADR-0031 already
  describes for Event's collection reads, not the all-or-nothing case `UserRoleResourceDefinition` answers.
- There is no `GET /api/events/{id}/infoPages` secondary endpoint - `Event` carries no `[HasMany]` back to
  `Page`/`InfoPage`, the same precedent already set by `Event.RoleGrants` having no `[HasMany]` back to
  `UserRole`. A client lists one Event's InfoPages via `GET /api/infoPages?filter=equals(eventId,'…')` instead.
